# Local planning, saved-plan Apply and recovery

This guide covers implemented accounts, source checks, verified PR/tracked-branch and explicit native planning, exact-plan approvals, saved-plan Apply, execution controls, formal recovery, evidence custody and process ownership. Native planning requires an assessed compatible stack and current execution gates. Actual company compatibility remains `not_assessed`. There is no production release; company adoption and deployment packaging remain later work.

## Verify locally

Run the README setup and test prerequisites, then:

```sh
make test-db-start
make check
make test-db-stop
```

`test-unit` includes Go race checks and static checks. The serial host integration/coverage runs allow 30 minutes for the expanded acceptance suite; CI still selects the complete, disjoint inventory across four bounded shards. `test-integration` runs against generated, marker-verified PostgreSQL databases using the real restricted runtime role. It covers tenant isolation, version-4/5/8 forward migrations through version 14, permanent ownership races, source fencing, encryption quotas, OAuth session binding, single-flight refresh, signed webhook deduplication and the local worker API journey. Source journeys replace external Git I/O; planning journeys additionally inject native/AWS I/O; the separate Linux suite exercises actual Git and process handling.

It mounts no database DSN, cloud credential, home directory or Docker socket. ## Schema and encryption key

Schema version 5 is a forward correction to the original version-4 foundation. It adds the narrow backend-binding, worker-identity, encryption-quota and OAuth-state helpers, immutable assignment snapshots, independent request receipts, worker tags and source-integration bookkeeping. The original four migrations remain unchanged. Serving never migrates implicitly.

Schema version 6 corrects evidence metadata before native planning is implemented. Migration 006 leaves 001–005 unchanged. Artifacts now have uploading/finalized/deleting/deleted/unavailable states, bucket identity, nullable incomplete-upload metadata, required exact version/hash/size at finalization, and deletion tombstones. Finalized object identity is immutable. Artifacts retain their original attempt and its owning operation; plan associations must belong to that same operation. This permits an assembling plan to rebind to a replacement preparation attempt while retaining immutable evidence from the failed attempt. Reviewed manifests, attempt attestations and log artifacts still require the exact owning attempt. Logs require either an artifact or an explicit gap.

A failed upload with a known exact version can enter deleting after its owning attempt closes, its holds are released and an exact-version cleanup claim exists. It can then receive a deletion tombstone without fabricating a finalization timestamp, hash or byte count. Claimed object identity is immutable, including for unfinalized uploads; deleting evidence cannot become usable again. This schema path does not implement cleanup eligibility scheduling or object deletion.

Holds reference an existing same-tenant plan, accepted operation, attempt, or recovery case, or an installation-wide backup capture. Active uniqueness includes the reason; released history remains. Backup captures record cutoff, digest and nonnegative artifact count, are owner-only, and retain tenant-scoped holds readable but not writable by the runtime. Cleanup claims reference the artifact's exact version, record retry outcomes, and block new holds. Evidence mutations take the existing coordination gate; held artifacts cannot be claimed or marked deleting/deleted. Startup checks the version and evidence protection boundaries. Migration 007 adds only a bounded final-log receipt to attempts, advancing the historical evidence baseline to schema version 7. Artifact custody now acquires active attempt holds, and plan-associated finalized evidence gains independent plan holds. Positive preflight closure releases only its attempt holds. Retention eligibility, cleanup and backup commands remain unimplemented.

Migration 008 advances the runtime to schema version 8. It preserves migrations 001–007 and adds immutable execution assignment snapshots, preparation/credential deadlines, provider-lock attestation links, producing-command artifact ordinals and exact spawn/stop facts. Readiness checks require the new integrity triggers. Narrow tenant-checked helpers validate only an attempt's own binding, observe the authority clock and place contradictory execution facts under attention; the runtime still cannot list or mutate global backend targets directly. Migration and serving remain separate commands.

Migration 009 preserves migrations 001–008 and alters all existing SECURITY DEFINER helpers in place to use `pg_catalog, cosmoformer, pg_temp`. Explicitly putting temporary relations last prevents runtime-owned temporary tables from replacing trusted application tables in helper lookups. Function identities, bodies and grants remain unchanged. Serving requires schema version 14 and rejects any definer helper with a different owner or search path. Run the explicit owner migration before restarting the runtime; serving does not repair database configuration. Regression checks cover durable encryption accounting with colliding temporary tables, cold/cached calls, unsafe configuration rejection, and version-8 upgrade of an already-open connection. This validation uses dummy data and ordinary tables, with no privilege-escalation payload or live database probe.

Migration 006 refuses a database containing version-5 artifacts or backup sets with `EVIDENCE_METADATA_RECONCILIATION_REQUIRED`. Version 5 lacks bucket and installation capture metadata; neither can be safely inferred. The migration visits each tenant under FORCE RLS and fails transactionally without advancing the version. Preserve the database and reconcile verified metadata through a separately reviewed migration before retrying; do not delete evidence to bypass this guard. Databases containing account/source/preflight/binding records without these legacy evidence rows upgrade directly. No backup capture or evidence deletion occurs during migration.

For a local installation that will store managed secrets, create a fresh raw 32-byte key outside Git and keep a separate protected backup. For example, from the repository root:

```sh
openssl rand -out .build/dev/encryption.key 32
chmod 600 .build/dev/encryption.key
COSMOFORMER_MIGRATION_DSN_FILE="$PWD/.build/dev/owner.dsn" \
  .build/tools/go/bin/go run ./cmd/cosmoformer migrate
COSMOFORMER_MIGRATION_DSN_FILE="$PWD/.build/dev/owner.dsn" \
  COSMOFORMER_ENCRYPTION_KEY_FILE="$PWD/.build/dev/encryption.key" \
  .build/tools/go/bin/go run ./cmd/cosmoformer register-key
```

Do not run the key-generation example over an existing key. `register-key` accepts only the migration owner and an installation without a registered key or prior key ledger. It never prints or stores key bytes in PostgreSQL. Replacing an existing key requires the later offline rotation workflow; this command refuses replacement.

Supply that same `COSMOFORMER_ENCRYPTION_KEY_FILE` when serving. Startup checks that its fingerprint matches the registered database identity. Account-only development can omit it; managed credential writes then fail closed. File contents must be exactly 32 raw bytes in a regular file readable only by its owner. Binary bytes are not text-trimmed.

Encryption authenticates the tenant, record, purpose and semantic revision. Browser API `{org}` and organization-scoped `{id}` parameters require lowercase hyphenated UUIDs, matching the database identity used for decryption. Uppercase, braced and compact spellings are rejected with 422 before encrypted settings can be written. Online writers durably reserve 4096-use blocks before encryption, consume one slot for every seal, burn unused slots on process exit and refuse reservations beyond the per-key limit. Failed writes still consume their reserved usage. Browser receipts contain neither credential values nor a fast hash of their submitted plaintext. Repeating a once-visible credential/secret write requires a new explicit change.

## Configure source checks

Use **Sources & workers** as an organization administrator:

1. Add a Bitbucket connection and register an exact canonical HTTPS repository URL, immutable Bitbucket repository UUID, project and tracked branch.
2. Add worker pools and explicit project/environment resource permissions. S3 permissions use the exact partition/bucket namespace and object key, including the lock object. DynamoDB permissions use the exact existing table ARN. Saving these references does not inspect, create or modify AWS resources.
3. Save the existing execution role ARN/account reference. Source preflight records it but never creates an AWS session.
4. Approve the exact built worker engine/version/image identity as an installation administrator. Enroll a worker into an allowed pool, save its credential privately and explicitly resume it.
5. Sync tracked inventory. Git cannot grant access to another project, environment, worker pool or secret. Configured teams still need Planner permission to request a source check.

For private Git, the scoped API accepts a repository read-only credential at `POST /api/v1/organizations/{org}/repositories/{id}/source-credentials` with `username`, `token` and `expected_revision` (zero for the first credential, otherwise the enabled credential revision from configuration metadata). Replacement disables the previous credential permanently. The value is encrypted and never readable through the browser. Managed secret replacement/enablement uses `PATCH /api/v1/organizations/{org}/secrets/{id}` with the expected revision and never returns the existing value; every accepted change advances semantic identity. Repository credential replacements advance the active record revision; stale expected revisions conflict even when a replacement receives a new credential ID. Workers request it only for their assigned repository/attempt and semantic revision. Broad OAuth credentials stay on the platform.

The worker's credential helper uses a private local socket and an owner-only attempt context containing identities and repository URLs. The supervising agent validates scope and registers returned credential values before giving them to Git. No platform bearer path, token URL, plaintext disk cache or direct helper-to-platform access is supplied to Git. Source stderr is discarded; retained preflight metadata is checked for known credential values before submission. This does not claim protection against arbitrary transformations by trusted repository code or a compromised worker host.

## Supported source subset

Use one root `cosmoformer.yaml`, version 1. Declarations require stable UUIDs, an explicit root, tracked branch, exact engine version, workspace and worker pool. Optional lists have explicit empty defaults; approval minimum defaults to one. Unknown/duplicate keys, multiple documents, anchors/aliases, custom tags, interpolation and files above 1 MiB are rejected. Administrator approval floors cannot be lowered by Git.

Preflight inspects HCL or JSON S3 backend declarations and ordered literal partial backend files without `init`. It rejects backend expressions, embedded credentials, custom endpoints, backend-specific assume-role settings and unsupported attributes. Default workspace keys remain byte-exact. Non-default keys use native-compatible path joining; distinct declarations that resolve to the same state or auxiliary lock/checksum object conflict permanently. No raw S3 object inspection or lock migration is performed.

Modules must be contained local directories or authorized Bitbucket HTTPS Git sources pinned to full commit IDs. Remote module reads use the same exact-commit and repository capability boundary. Registry, SSH, floating-ref, submodule and LFS-pointer sources are unsupported. Git hooks, user/system configuration, redirects and smudge filters are disabled. Source files are bounded to 1 MiB each, 64 MiB total and 10,000 files; module traversal is bounded to depth 32 and 256 directories. Escaping symlinks, Git/native administrative paths and special files are refused. Provenance includes sorted paths, Git file modes and exact file/symlink digests.

Secret destinations cannot override worker/AWS/Git/native control variables. `TF_VAR_` destinations must name literal sensitive, non-ephemeral root variables. Preflight carries secret references only and has no execution-input/secret-value delivery route.

## Bitbucket connection and ingress

An administrator configures the OAuth consumer key/secret, webhook signing secret and expected hook UUID in **Bitbucket OAuth settings**, then chooses **Connect Bitbucket**. The callback is the configured application origin plus `/oauth/bitbucket/callback`. State is one-use, expires in ten minutes and is bound to the initiating local administrator/session/integration; it cannot sign in a user or select an arbitrary return URL. Configure only the selected `repository`, `pullrequest:write` and `webhook` OAuth scopes. Returned scope sets are checked before credentials are accepted. See [Bitbucket authentication and scopes](https://developer.atlassian.com/cloud/bitbucket/rest/intro/).

Rotating refreshes use a durable per-integration claim. A concurrent refresh cannot reuse the old refresh token. A failed or interrupted claim requires explicit reconnection; elapsed time is not evidence that retrying a rotating token is safe.

The ingress route is `/webhooks/bitbucket/{org}/{integration}`. It verifies the expected hook UUID, constant-time HMAC-SHA256 over the bounded original body and the registered repository UUID before committing a deduplicated receipt and reconciliation job. A receipt never launches a native command. Supported events are push and PR create/update/fulfill/reject. Reusing a delivery UUID with a different body is a conflict. See [Bitbucket webhook configuration](https://support.atlassian.com/bitbucket-cloud/docs/manage-webhooks/). No external webhook was registered or altered by the local implementation/tests.

The platform services source jobs only while running. It performs five-minute sweeps of tracked branches and known open PRs, coalesces obsolete unclaimed source requests and accepts source facts through ticket/revision fencing. Sweeps repair missed updates and closures for known PRs; discovering a new PR still requires its webhook or an explicit PR request. Incomplete changed-path information conservatively selects only otherwise authorized, compatible tracked declarations. Root `cosmoformer.yaml` changes select all relevant stacks; exact complete diffs also include stack roots, declared prefixes, input files and known tracked local-module paths. Without a verified tracked module closure, path exclusion is conservative. Path selections are retained per source-facts revision so unchanged sweeps cannot drift from a prior decision. Authenticated changed-source facts are committed before manifest parsing/import, so a missing, invalid or unauthorized new declaration still invalidates old queued/active preflight authority without replacing accepted inventory. Retargeting a PR away from the tracked branch also records the actual destination and revokes prior authority before declining replacement work. Later work creation rechecks the observation ticket, revision, repository configuration and elapsed read budget. Closed/changed source invalidates prior authority; source reversion creates a new revision rather than reviving earlier evidence. Automatic work has an explicit repository automation context, never a Bitbucket actor impersonating a local approver.

Repeating an accepted sync or preflight request with the same idempotency key and body recovers its saved response after checking current authorization. It does not reread Bitbucket or create another source observation; changed request bodies conflict and revoked access is still denied. A new source check requires a new request key.

PR feedback reuses its stored comment ID and looks for a stable marker before recovering an uncertain creation response. Pagination and credential-bearing destinations are bounded. Writes are serialized per PR across platform processes, and jobs for superseded source revisions are discarded before provider I/O. Feedback failures remain visible in **Source delivery**, retry with bounded jitter/backoff and honor supported Retry-After responses; exhausted delivery needs an explicit retry. Feedback does not grant access, count as approval or alter infrastructure.

## Worker identity and outcomes

`make worker-image` builds only a local OpenTofu reference worker image. The image requires Linux amd64, the pinned Git package and a verified exact runtime. It runs without root. A separately buildable Terraform reference download is pinned in `deploy/worker/runtimes.json`; changing the build arguments must still match one of the recorded engine/version/checksum tuples.

The protected `COSMOFORMER_TOKEN_FILE` contains JSON with `worker_id` and `token`, as shown once during enrollment. It must be readable by the worker UID and not by group/others. Configure `COSMOFORMER_PLATFORM_ORIGIN` as an exact HTTPS origin, `COSMOFORMER_RUNTIME_ID`, the operator-verified `COSMOFORMER_IMAGE_DIGEST`, `COSMOFORMER_EXPECTED_BOOTSTRAP_PRINCIPAL` as the approved bootstrap IAM role ARN, and optionally an absolute `COSMOFORMER_ATTEMPT_DIR`. No database DSN, encryption key or cloud credential is supplied to the worker. The reported image digest is a trusted operator binding, not remote attestation.

Current workers advertise `preflight` and `execution`; existing preflight-only agents remain supported. Preflight assignments default to a five-minute nonrenewing elapsed budget; a response cannot extend it. Admission generations and agent instances fence replacements. Poll and ordered transition replays preserve accepted identities; changed accepted data or sequence gaps are rejected. Claim ownership remains separate from last-contact time. A restarted worker cannot take over an unresolved attempt.

“Source check passed” means exact-source inspection and binding were accepted. It establishes neither state contents nor infrastructure safety. Positively reaped preparation failures may be explicitly retried with a fresh attempt. An uncertain process group retains ownership and requires operator stop evidence; timeout, pause, credential revocation and missing acknowledgements never release it. Execution controls and formal recovery follow the procedures below. Native start permissions support the fixed planning and saved-plan Apply sequences.

## Evidence storage and log operations

Account/source-only development leaves all artifact settings unset. To configure custody, set `COSMOFORMER_ARTIFACT_BUCKET`, `COSMOFORMER_ARTIFACT_REGION`, and `COSMOFORMER_ARTIFACT_EXPECTED_OWNER` together. Partial/invalid settings fail startup. Use a separate private AWS S3 bucket, not a native backend/state bucket. Every storage operation checks expected ownership, bucket region, enabled versioning, AES256 default encryption and all four public-access-block settings. The platform uses only EC2 instance-role credentials with the standard IMDS endpoint; environment credentials, shared profiles and endpoint overrides are not accepted. No storage check contacts AWS when storage is unset; tests use injected synthetic endpoints only.

Custody accepts 64 MiB artifacts and 1 MiB log envelopes. Four concurrent storage operations bound upload memory; each temporary file is at most 64 MiB. Uploads spool to owner-only temporary files, verify length/SHA-256, and stream with one 8 MiB multipart part in flight. Reads spool and verify exact VersionId, length, encryption and SHA-256 before returning bytes, then recheck current authorization. Missing/corrupt versions become unavailable; transport/configuration failures fail closed without substituting latest. Temporary files are removed on normal completion/error; host crash cleanup of temporary files remains an operator responsibility.

PUT `/worker/v1/attempts/{id}/artifacts/{upload}` streams octet bytes with `Artifact-Kind`, `Content-Length`, `Expected-SHA256`, bearer authorization and exact `X-Worker-ID`, `X-Worker-Generation`, `X-Agent-Instance` headers. Finalize POST and worker artifact GET use the same identity headers. Finalize binds request ID, kind, hash and size. A retained exact receipt supports replay after response loss. A matching reserved upload with no retained version returns UPLOAD_INCOMPLETE: use a new upload ID for the identical bytes; never guess latest or overwrite its key. Worker delivery rotates its upload ID only for this explicit PUT response; response loss and other conflicts preserve the original identity. Preflight admits only log segments; planning execution admission additionally requires explicit native intent and compatible fit. Retained-plan preparation reads require an exact Apply-plan association and existing operation/attempt holds acquired under the gate before acceptance and claim. Reads do not create execution attempts.

A durable `log_segment` artifact contains a closed JSON segment envelope: sequence, byte_start, byte_end, and either text or gap `{reason,unknown_extent}`. Finalization appends only the next sequence and contiguous redacted byte range. Failed/out-of-order finalizations remain unready. Gap records have no text/artifact reference. The worker's `ArchiveSegment` preserves upload identity for caller retries; preview delivery never acknowledges custody. The worker queue coalesces small reads into fixed-size blocks, reserves metadata and snapshot space within its 8 MiB budget, and limits retained segment count. It returns explicit overflow ranges, continues draining output, and does not claim delivery on failure. Each pipe preserves partial UTF-8 characters before masked chunks are combined. The caller retains unacknowledged segments; worker restart/lost buffers require unknown-loss reporting, not reconstructed output.

POST attempt `/log-preview` accepts console stream, agent epoch, sequence, byte_start and bounded text/gap. Browser GET `/api/v1/organizations/{org}/runs/{run}/logs` requires attempt_id and limit_bytes (1–262144). Preview text is limited to 65536 bytes/request, 1 MiB/attempt and 32 MiB total with bounded entry counts. The platform owns preview epochs; eviction/restart resets cursors to durable archive progress and reports loss. Cursors are bounded subject-checked positions, never authority. Archive completion requires a positively closed attempt, a matching final worker receipt and no durable gap/unavailable artifact. An omitted final receipt records an explicit unknown gap. The single-console final receipt uses last_sequence=-1 for an empty archive. Log polling and evidence reads do not renew browser idle expiry.

GET `/api/v1/organizations/{org}/artifacts/{artifact}/content` requires current Viewer scope and, for all non-log artifact kinds in this milestone, separate raw_evidence_read. Administrator ownership alone grants neither. Downloads have protected disposition and no-store headers; permission revocation cannot retract bytes already delivered. Validated sanitized Changes are available through the exact ready-plan Changes route. Direct artifact downloads retain raw permissions, including unready or rejected normalized artifacts.

Known-secret registration is atomic and bounded to 4096 terms/262144 bytes. Credentials register in the shared attempt registry before helper delivery. Each console pipe masks independently across reads before preview/archive buffering; raw JSON stdout and credential-helper output are excluded. Exact masking does not identify transformed secrets, unknown historical values or malicious code exfiltration. The capture publisher flushes every second and retains each segment/upload ID until acknowledgment. Native planning now connects process capture to archive custody and exact command/result reconciliation. Raw schema/plan JSON never enters the console stream.

## Native planning

Migration 010 advances the supported schema to 10. Existing operations retain source-only intent; the new intent and ready-plan evidence identities are immutable. It reuses the existing scoped target-epoch helper. No earlier migration is rewritten.

`POST /api/v1/organizations/{org}/stacks/{id}/plans` preserves Check source when intent is omitted or `source_check`. Only `intent: "native_plan"` on a **new** request authorizes planning. Intent cannot be upgraded on an existing operation. Reconciliation jobs remain source-only. Planner authority, accepted tracked declarations, current source observations, enabled exact grants, approved runtime/routing, backend ownership and stack assessment `compatible` are required. Company assessment remains `not_assessed`; this milestone adds no assessment bypass or automatic compatibility decision.

Execution claims acquire exact worker and backend reservations and create an assembling plan. Each execution uses a fresh private directory, hashes all checked-out files in the pinned module closure, verifies installed module copies, and rechecks inputs around initialization/sealing and subsequent commands. Explicit backend and variable file paths are repository-relative even when native execution uses a nested stack directory; preflight, manifest identities and native arguments resolve the same files in declared order. The environment starts empty, uses fixed platform paths/Git/provider-install settings and guarded secret bindings, and receives only the fixed temporary AWS session. No inherited CLI flags, endpoints, provider cache, upgrade, workspace creation, arbitrary command or automatic replan is available.

The sequence is init → seal → schema → saved plan → show. A committed provider lock is readonly and retained byte-for-byte. A generated native lock is sealed and retained separately. An absent lock is accepted only with an empty external-provider set; later unexpected lock content fails. Supported analysis profiles are `opentofu-1.13.8-warnings-v1` and `terraform-1.17.1-warnings-v1`; exact AWS 6.41.0 full-schema fingerprints are listed below. Tested S3-native, DynamoDB and dual lock profiles retain their existing exact namespace/grant requirements. KMS execution remains blocked.

Each native command uses a separate process group and a request-anchored, single-use permission, with the final elapsed-time check held through exec. The supervisor reports exact PID/PGID, exit or signal, group emptiness, and drained or explicitly gapped pipes. Raw schema/show output is bounded to 64 MiB in protected files; overflow is failure. Console output uses shared known-value redaction and archive helpers. Deadline expiry sends the direct native parent one SIGINT and never escalates to SIGKILL. A surviving group or unproven stop opens attention and retains reservations and recovery evidence holds. Lost contact alone retains ownership. A lost permission response cannot be reconstructed into a never-started proof; no new ordinal, renewed permit or execution retry bypasses it.

Readiness requires finalized exact-version pre-init spec, manifest, native binary plan, raw plan JSON, schema, normalized Changes, findings, and provider lock when present, all linked to the same execution and command stages. Analysis IDs are opaque random UUIDs retained in a non-native identity list. The platform independently checks retained analysis and current managed-secret values, then atomically rechecks source/state epoch, authority, inputs, exact artifact availability and required holds. Ready evidence and its manifest/TTL identities cannot be rewritten. `COSMOFORMER_PLAN_TTL_HOURS` defaults to 168, range 1–720; readiness snapshots current PostgreSQL time once. `COSMOFORMER_PLAN_SECONDS` defaults to 1200, `COSMOFORMER_APPLY_SECONDS` to 2400 and `COSMOFORMER_PREFLIGHT_SECONDS` to 300; configured caps must be 30–3300 seconds and fixed-session conservative bounds can further deny preparation. No new command or ready plan is admitted after its attempt budget. Positive stop/failure reports remain accepted after authority/budget loss.

`GET /api/v1/organizations/{org}/stacks` and `/runs` support project/environment/stack filters, bounded limits and stable `before` cursors; scopes are applied before limits. `/runs/{id}` returns historical source, operation outcome, queue explanation, attempts, plan usability and evidence status separately. Attempts and separately authorized raw metadata use bounded 100-entry pages with `attempt_before`/`artifact_before` cursors and explicit continuation controls. The `/plans` list uses the same scope filtering. Installation or scope administration alone grants no ordinary run/evidence visibility.

`GET /api/v1/organizations/{org}/runs/{id}/changes?plan_id=<uuid>&revision=<revision>&manifest_digest=<sha256>` binds the exact plan/revision/manifest (the digest query remains optional for existing clients). It resolves the normalized artifact ID from the accepted execution result, never a latest artifact. Finalized historical Changes remain reviewable after invalidation or expiry; review does not change eligibility. Unfinalized, missing, deleting or corrupt evidence has no raw/latest fallback. Storage reads recheck current permission after I/O. Raw artifact download still requires a separate current raw-evidence grant plus Viewer access. Existing check/status reads distinguish native intent, `PLAN_READY` and `NO_CHANGES`; output-only updates count as changes.

The SPA offers project Stacks/Runs, stack source/request actions and run Overview/Changes/Logs, without placeholder feature routes. Exact run context survives deep links and refresh. Logs use bounded cursor polling with pause/follow, archive continuation, preview-reset notices and explicit known/unknown gaps. The 512 Ki character / 500 segment browser window is a display limit, not a claim of durable loss. Background reads do not renew idle sessions; denied access and logout/expiry clear protected content. Sign-in requires a new explicit planning action. Light/dark and narrow layouts are covered by Chromium/Firefox screenshots against local HTTPS and synthetic isolated evidence.

Coverage verification is independently derived from the retained schema/resource identities and sanitized values. Provider identity/version/schema alone are insufficient: status, unsupported variants and unknown/hidden resource annotations must match the conservative result. Additional worker-only AWS/Git masking may add uncertainty or hide a variant label, but may not remove the unsupported limitation or promote generic/partial coverage to complete. Forged coverage blocks readiness; finalized artifacts are never repaired in place and require a fresh plan.

The warning correction is independent of execution wiring: display masking no longer changes the private validated resource type used for classification. RDS deletion/replacement stays Critical and selected RDS/network rules remain effective when type/address displays are hidden. No unmasked type is serialized. Retained verification also preserves validated native resource mode privately: data sources are checked against their data-source schemas and receive no managed-resource warnings. Metadata collisions or unsupported required analysis fail closed.

Verification has two separate suites: real platform/worker protocol plus marker-verified isolated PostgreSQL with injected native/AWS I/O, and actual pinned engines/providers in network-isolated native containers with no database, host credentials or mounts. Linux process tests additionally exercise real subprocesses, raw-output bounds and graceful-only deadline handling. All fixtures are synthetic. No live AWS/company plan, adoption, provisioning, publication or deployment is implied.

Scheduled cleanup and packaging remain out of scope. Saved-plan Apply uses the separate guarded path below. Cancel, Force Stop and formal recovery now use the guarded workflow below; do not restart or reassign unresolved attempts to bypass reservations. Process groups assume native/provider children do not detach and are not an OS isolation boundary. Arbitrary transformed/unknown historical secrets remain outside exact-known-value protection.

## Native protocol boundary

Production workers advertise source preflight and planning execution. The control routes for execution inputs, preparation, manifest sealing, start permission, command events, results and control acknowledgements operate on an existing exact worker/generation/agent/attempt claim; they do not independently create executable work. New planning journeys use actual scheduling; protocol-focused integration tests also install synthetic claims using the real database constraints and restricted runtime role. There is no temporary executor or execution enablement setting.

Execution inputs recheck current account/automation authority, exact grants, secret scope, enabled state and semantic revisions. Responses use no-store and are excluded from assignment/replay/audit records. Worker delivery registers complete values and JSON scalar leaves before returning values for child use; registry or environment limits fail preparation. Preflight cannot retrieve execution inputs. ## Plan analysis library and coverage

`plan.Analyze(rawPlan, providerSchema, options)` validates protected bytes and returns sanitized Changes or an error with no partial result. Resource/output IDs are caller-allocated opaque UUIDs, retained for that attempt and reused for reanalysis. Do not hash addresses, labels or secret bytes into public IDs. A known-secret address becomes `hidden` with its opaque ID intact. Findings use SHA-256 of the rule version, opaque resource ID, rule ID and canonical safe path. Results and findings sort deterministically; resource/drift input ordering cannot change IDs. Drift has its own list, contributes no proposed-action counts and emits no apply warnings.

The validator rejects duplicate decoded object keys, invalid UTF-8/unpaired Unicode escapes, trailing JSON, missing required change/sensitivity fields, unsupported actions/native versions and invalid selected shapes. It uses terraform-json **v0.29.0** only after raw validation and preserves JSON numbers. Limits are 64 MiB per input/output, depth 96, two million JSON nodes, a conservative 64 MiB expanded-scalar/key budget, 10,000 resources per collection and 4,096 expanded ingress atoms per resource side. Decimal expansions are capped at 16,384 bytes before allocation. Exceeding any bound fails analysis without truncation. Incomplete/deferred plans and action-invocation extensions are unsupported. Empty provider sets may omit `provider_schemas`, matching both pinned engines; explicit null/wrong-shaped schema maps are rejected.

Changes distinguish `known`, `unknown`, `hidden`, `null` and `absent`. Known numbers use canonical decimal strings, including large integers and exponent notation; known booleans remain booleans. A sensitive path on either side hides both sides. Schema sensitivity supplements native sensitivity. Ambiguous shapes, changed sets with nested sensitivity, or changed collection lengths hide their parent; safe siblings outside that parent remain. Ordered nested lists with unambiguous native sensitivity retain safe sibling fields. A changed collection containing a known secret hides its parent rather than guessing which value is the other logical side after a reorder. Replacement order and safe replacement paths survive normalization; an empty replacement path denotes a hidden parent when no safe descendant path can be retained.

Managed secrets, AWS credentials and Git values must finish registering before analysis or child use. The shared registry is longest-first and remains bounded to 4,096 distinct terms and 262,144 total bytes; failure denies delivery/analysis rather than weakening matching. JSON-form `TF_VAR_` secrets additionally register nonempty decoded string leaves and canonical number/boolean leaves. Exact scalar matches or contained known values hide both before/after fields; matching keys hide their parent. Quoted identifier tokens are checked after decoding their structural escapes as well. The final full-result scan includes metadata, safe paths and message arguments. Very short values can redact unrelated fields or collide with mandatory metadata/fingerprints; such a collision fails closed instead of emitting a leaking artifact. Successful results include a broad-redaction notice. Exact matching does not track arbitrary transformations, unknown historical state secrets, deliberate `nonsensitive()` disclosure or executable repository exfiltration. Results explicitly carry that limitation; no universal taint-tracking or safety claim is made.

### Recovery procedure

1. Inspect the exact run and attempt, current control delivery, logs and protected evidence. If stopping is necessary, request Cancel or separately confirmed Force Stop. These actions do not promise rollback or successful termination.
2. An unresolved agent restart, contradictory protocol facts or explicit **Escalate to recovery** opens formal recovery for the exact stack, permanently bound target and originating attempt. The recovery event advances the state epoch once and invalidates earlier normal plans. Retried restart reports do not advance it again. Worker/backend reservations remain until independent stop proof. Rejected conflicting facts cannot overwrite accepted command history.
3. Independently establish process/host stop. Agent-method evidence is accepted only when the original attempt's accepted protocol facts positively account for every permission; an issued/lost-response permission is insufficient. A zero-permission native closure requires an accepted native-result digest; a prior host/operator closure cannot be relabelled as agent proof. Contradictory stop facts require host/operator authority. Host and operator methods are explicitly **manual attestations**, not automatic verification: independently check the recorded process group, descendants and host/VM ownership, and retain evidence in a protected record. Process groups assume trusted native/provider processes do not detach. If that assumption fails, use independent host/VM evidence.
4. Submit bounded non-secret stop/reconciliation statements and protected references with the current case revision. Keep raw state, environment values and credentials out of statements. References must be opaque record identifiers or credential-free HTTPS locations without query strings or fragments. Only separate current raw-evidence permission exposes protected references in reads and mutation retries. Retried evidence, approval and clearance responses project current permissions and counts while preserving the original approval event; new receipts retain no protected context. Evidence versions retain the submitter, authority and prior content. Edits advance the evidence revision and invalidate counting votes. No native stop event is fabricated from a manual attestation.
5. Proven stop copies required attempt, plan and available log evidence to recovery holds **before** releasing only the matching temporary worker/backend reservations. The stopped unresolved attempt closes as `unknown`; permanent stack bindings and backend resource claims remain. The matching old agent admission is fenced and paused unless a different exact reservation already owns that worker. Resume/re-admit only after confirming the old process is stopped. Re-submitting old evidence cannot release a newer attempt's reservations. Missing final logs receive an explicit unknown-extent gap.
6. Reconcile infrastructure and state independently; mark reconciliation complete only when the retained evidence supports it. Process stop alone leaves infrastructure outcome unknown. Recovery planning requires verified stop plus current Plan or Apply authority. Request diagnostic planning from the recovery panel; it verifies current source and normal input/runtime/resource gates. Its run, operation, manifest and retained artifacts preserve the case and evidence revision, and the result remains `recovery_only`. Evidence changes retire unclaimed stale diagnostic requests. An uncertain diagnostic attempt needs its own exact independent stop proof; it cannot borrow the originating attempt's release.
7. Obtain the current effective minimum of distinct eligible recovery approvers for the exact evidence revision. An eligible submitter/author counts once. Account, membership or scoped approval-grant loss immediately reduces the count; restoring eligibility may count a still-current vote. Recovery approval and clearance make no Bitbucket read. Maintenance or an unreliable-clock state blocks new recovery approvals, clearance and diagnostic planning; evidence and independent stop reports remain available. Clearance also requires current scoped Apply permission, verified stop, complete reconciliation and no unresolved associated execution/diagnostic work.
8. Explicitly clear the case. The originating operation leaves `needs_attention` as failed with reason `recovery_completed`; accepted command/outcome history is retained. Recovery holds release only after associated attempts have closed. No recovery plan is promoted and no normal plan or approval is revived. Request a **new normal plan after clearance**, obtain new normal approvals, and use the later saved-plan Apply milestone when available. Pre-clearance normal requests cannot become deployment candidates by waiting through recovery.

An unbound source-only preflight has no execution-role session, native permission or backend target. Restart/escalation retains its exact worker reservation and marks source preparation uncertain without creating a backend target or recovery case. Its workspace accepts independent host/operator source-process stop proof; after proof it closes failed/unknown and needs a new plan request. No recovery approval ceremony or backend binding is invented for that source-only case.

Earlier completed init is not an Apply. There is no automatic replacement permission or command retry.

Uncertain ownership retains exact reservations and opens recovery; timeout, signal delivery or revoked credentials are not stop proof.
